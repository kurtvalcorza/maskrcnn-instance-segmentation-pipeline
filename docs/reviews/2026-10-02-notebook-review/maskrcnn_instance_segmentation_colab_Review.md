## Executive assessment

The engineering of the default path is sound and its claims are honest. The checkpoint is pinned by SHA-256 and
verified before a strict load; the input and dataset validators refuse bad input with messages that name the rule;
the split is asserted leak-free; the re-headed baseline is measured before training and is correctly described as a
floor; the loss is labelled optimisation evidence only; box and mask AP are both reported; the adapter export is
reloaded onto a fresh base and compared instance by instance with a stated tolerance; and the closing cell says what
a green run does and does not establish. The exact blob under review has a clean-runtime Kaggle T4 record, and a CPU
execution in this review reproduced its COCO-scene and degenerate-probe numbers to the printed precision
(stop sign `box_iou` 0.944 / `mask_iou` 0.984, sports ball missed, noise 2 instances at 0.05: umbrella 0.26,
bear 0.13).

Three Major problems stop it being ready. **Run all does not complete in one pass**: the recorded Kaggle T4 run
stopped at the install cell's own restart guard (`cuda-bindings 12.9.4 → 13.4.3, numpy 2.0.2 → 2.5.3`) and passed only
after the executor restarted the kernel. **The declared `GUIDED` layer is largely absent**: no "how to use", intended
learner, roadmap, prediction prompts, interpretation checkpoints, troubleshooting or conclusion prompt, and 1,225 lines
of carried package code are not marked as infrastructure that may be run without study. **The notebook's only
experiment ("Try next") silently runs a different experiment**: re-running the fine-tune after changing
`FREEZE_BACKBONE` or `EPOCHS` continues training the already-adapted model while the run record reports only the new
call, and the metric the learner is told to compare (held-out mask AP) is already at its ceiling of 1.0 in the default
run. Six Minor findings cover BYOD recovery messages, a stale runtime claim, unexplained saturated and low-threshold
results, evidence gaps, an undocumented environment variable and prose that hard-codes form-field values.

No finding here says the recorded default-path numbers are wrong.

## 5. Findings

### Major

#### MRC-M1 — `Run all` stops at the install cell; the recorded run needed a manual restart

- **Cell/section:** Section 1, cell 3 (generated by `tools/build_notebook.py` lines ~440–475); opening "Run all" paragraph (cell 0).
- **Observed issue:** Cell 3 `pip install`s the five pins into the running kernel, then raises `RuntimeError('Core dependencies changed while older modules were loaded: … Restart the runtime, then rerun from the top.')` when a distribution already imported by the hosted image changes. On the documented hosted image that always happens: the Kaggle T4 record of this exact blob shows pass 1 stopping after 377.1 s (cuda-bindings 12.9.4 → 13.4.3, numpy 2.0.2 → 2.5.3) and pass 2 succeeding only after a restart.
- **Consequence:** A learner who chooses Run all, as the opening tells them to, gets a stopped notebook after six minutes; the opening promises the opposite. The guard is correct engineering, but it converts the restart into a documented manual step, which RUN1/RUN10/ENV6 forbid.
- **Evidence:** Documented execution (`docs/release-verification.md`, 2026-09-25 row: "pass 1 377.1 s stopped after the install cell … kernel restarted after the install cell as the notebook instructs"); source inspection of cell 3.
- **Recommended correction:** Replace the in-kernel install with the fleet's **uv isolated-environment** pattern: a carrier cell bootstraps uv, creates `uv venv --managed-python --python 3.12.12 <ROOT>/env`, installs a hash-locked requirements file with `uv pip install --require-hashes --only-binary :all:`, and runs the workload in that environment, so the kernel's preloaded NumPy/torch are never replaced. Reference: `ast-audio-classification-pipeline/tutorials/DIMER_Sound_Event_Classification_Workshop.ipynb` on `origin/main`. Change it in the generator (`tools/build_notebook.py` install-cell section) and regenerate.
- **Acceptance check:** A fresh Colab T4 (or Kaggle T4) Run all of the regenerated blob completes every code cell in one pass with no error output and no restart, and that run is recorded in `docs/release-verification.md` against the new blob id.
- **Spec:** RUN1, RUN10, ENV6, REL2, REL11 (MUST).

#### MRC-M2 — Declared `GUIDED`, but the guided layer is largely absent

- **Cell/section:** Opening (cells 0–1), Section 2 (cells 4–7), every stage section, closing cell 30 (`tools/notebook_template.py`, `tools/build_notebook.py` prerequisite and section text).
- **Observed issue:** Static scan of all 17 markdown cells: no "How to use this notebook", no intended learner, no roadmap, no prediction prompt, no interpretation checkpoint or sample answer, no troubleshooting section, no conclusion template, no glossary. A self-paced learner new to instance segmentation is never asked to predict or explain, cannot tell essential from infrastructure, and has no route when the install cell stops (MRC-M1). - **Recommended correction:** Either (a) add the guided layer in the generator: a "How to use" cell naming the learner, Run all and form fields, a roadmap, an **Infrastructure** callout on Section 1–3 cells (collapsed where supported), a prediction prompt before Sections 4, 7 and 9, an expected-result note after Sections 3, 9, 10 and 11, two interpretation checkpoints with collapsible sample answers (e.g. "why is the baseline near zero?", "what does mask AP 1.0 on 10 drawn images tell you?"), a short troubleshooting section (install/restart, download, CPU time, BYOD errors) and a conclusion template; rewrite the objectives with observable verbs; or (b) declare `REFERENCE` mode, which this content fits.
- **Acceptance check:** The regenerated notebook either declares `REFERENCE`, or contains each of GDL1–GDL4, GDL7–GDL9, GDL11, GDL13 and GDL14 in a cell a reviewer can point to, and every learning objective uses an observable verb.

#### MRC-M3 — "Try next" runs a different experiment from the one it describes, and compares a saturated metric

- **Cell/section:** Closing cell 30 ("Change `FREEZE_BACKBONE` to `False` and compare held-out mask AP and runtime, or change `EPOCHS` and watch where held-out mask AP stops improving"), with cells 15, 17, 19, 21 (`tools/notebook_template.py` lines ~210, ~269, ~519).
- **Observed issue:** (1) `FREEZE_BACKBONE` is a form field in the fine-tune cell 19, `EPOCHS` in the dataset cell 15, but the re-headed `adapter` is created only in cell 17, and `finetune` "mutates this pipeline in place". No rerun instruction exists anywhere in the notebook. Following "Try next" the natural way — edit the field, re-run the fine-tune cell and the evaluation cell — fine-tunes the *already adapted* model again. Directly executed (CPU, reduced config): after the default fine-tune the adapter's `adapted` flag was already `True`; re-running cells 19 and 21 with `FREEZE_BACKBONE = False` applied a second epoch on top of the first, the printed run record said `epochs: 1, freeze_backbone: false`, and the table compared the stack with the original baseline (`mask_ap` 0.0 → 0.1534, where the first epoch alone gave 0.0). The same applies to changing `EPOCHS` in cell 15. Re-running cell 17 first does reset the predictors (verified), but nothing tells the learner to. (2) The comparison metric is already at its ceiling: in the recorded default run held-out `mask_ap`, `mask_ap50`, `mask_ap75` and every per-class AP50 are 1.0, so "compare held-out mask AP" or "watch where it stops improving" cannot show a gain from either change.
- **Consequence:** The notebook's one change-and-compare activity produces an invalid comparison (two schedules stacked, recorded as one) and, done correctly, an uninformative one. A learner is likely to conclude that unfreezing or more epochs "made no difference" or that the extra epochs explain the result, which the experiment does not support.
- **Evidence:** Direct CPU execution, reduced config (`results.json` → `active_learning`); source inspection of `finetune` (pipeline.py, "Mutates this pipeline in place"); documented execution for the saturated 1.0 rows.
- **Recommended correction:** In the generator: put each experiment's controls in one place and state the rerun range ("change the field, then re-run from Section 7"), or have the fine-tune cell re-head a fresh pipeline from `WEIGHTS_DIR` each time it runs; record the cumulative schedule if stacking is intended. Compare on a metric with headroom — for instance box `ap`/`mask_ap75` (0.87 box `ap` in the recorded run), a harder held-out set, or fewer epochs — and give the learner a prediction prompt and an expected-result note.
- **Acceptance check:** Following the documented "Try next" steps exactly from a completed default run yields a fine-tune that starts from the re-headed checkpoint (predictor weights equal to a fresh `from_pretrained(class_names=…, seed=SEED)`), the printed run record matches the schedule actually applied, and the compared metric is below 1.0 in the default run.
- **Spec:** GDL10, UX5, FT6 (MUST: epochs recorded where applicable), SRC2 (MUST: no hidden out-of-order dependency).

#### MRC-m1 — Some BYOD failures surface as raw exceptions

- **Cell/section:** Section 13, cell 29; `read_detection_records` in the carried `pipeline.py`.
- **Observed issue:** Direct probes (`results.json` → `recovery_probes`): a BYOD image that is not an image raises `PIL.UnidentifiedImageError` because cell 29 opens it before `validate_inputs`; an `annotations.json` naming a missing mask file raises a bare `FileNotFoundError` from PIL; boxes in normalised [0, 1] coordinates are refused as "record 0 mask 0 extends outside its box", which names the rule but not the likely cause (pixel vs normalised coordinates). - **Acceptance check:** The three inputs above each produce a `ValueError` naming the file or rule and the corrective action, and no PIL traceback reaches the learner.
- **Spec:** DAT19 (MUST), UX10.
